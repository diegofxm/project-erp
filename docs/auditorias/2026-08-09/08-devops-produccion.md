# Agente DevOps / Preparación para Producción

## ✅ Lo que está bien implementado

- **Existe un endpoint de salud**: `erp/cmd/server/main.go:433-437` registra `GET /health` y devuelve `{"status":"ok","service":"cofacture erp"}` con `200 OK`. Sirve como probe mínimo de "el proceso está vivo".
- **Configuración por entorno vía variables de entorno, documentada y con comentarios de contexto real** en `erp/.env.example`: distingue explícitamente Postgres local (`DATABASE_URL=postgresql://postgres:password@localhost:5432/erp_dev`) de Postgres gestionado en producción (comentario con Neon, `...neon.tech/dbname?sslmode=require&channel_binding=require`), y SMTP de desarrollo (Mailtrap/Mailpit) vs. producción (servidor propio / Mox / Postfix). Incluye incluso una advertencia operativa concreta y no genérica: "no le pongas comentarios `# ...` al final de la misma línea de un valor activo — godotenv (local) sí los recorta, pero systemd `EnvironmentFile=` NO" (`erp/.env.example`, bloque de SMTP) — evidencia de que el despliegue real ya pasó por un systemd unit file en algún punto, aunque el archivo de esa unit no está en el repo.
- **Las migraciones de esquema se aplican automáticamente al arrancar el proceso**, por módulo, vía `golang-migrate`: `erp/internal/*/infrastructure/persistence/postgres/migrate.go` (14 módulos). No requiere un paso de deploy manual aparte para el esquema.
- **Multi-tenant con `company_id` compartido, aislado a nivel de aplicación, no de base de datos** — patrón consistente: 262 referencias a `company_id` en los repositorios Postgres, y `erp/internal/shared/tenant` inyecta el `company_id` activo en el contexto de cada request (`tenant.Middleware`, ver `WithCompanyID`/`GetCompanyID`). No hay schema-per-tenant ni bases de datos separadas — es el modelo esperable para esta escala y evita la complejidad operativa de aprovisionar infraestructura por cliente.
- **Pool de conexiones vía `pgxpool` con configuración explícita del huso horario por conexión** (`cmd/server/main.go:495-498`, `SET TIME ZONE 'America/Bogota'` en `AfterConnect`), evitando bugs de fecha/hora silenciosos en un dominio (facturación DIAN) donde la fecha es legalmente sensible.

## ⚠️ Lo que existe pero tiene problemas / riesgos

- **El `/health` es un placeholder estático, no un healthcheck real.** `erp/cmd/server/main.go:433-437` no consulta el pool de Postgres (`pool.Ping`) ni ninguna dependencia externa (SMTP, TRM, DIAN) — siempre responde `200 ok` aunque la base de datos esté caída. Cualquier orquestador (balanceador, systemd `Restart=on-failure` con watchdog, monitor externo) que confíe en este endpoint para decidir si el proceso está sano recibirá falsos positivos.
- **El pool de Postgres se crea con `pgxpool.ParseConfig` sin fijar `MaxConns`/`MinConns` explícitos** (`cmd/server/main.go:489-501`) — queda en el valor por defecto de pgx (aprox. 4 × núcleos de CPU disponibles, o el límite del `DATABASE_URL` si se pasa por query string). Con multi-tenant de esquema compartido, si crece el número de empresas concurrentes sin ajustar este límite explícitamente (y sin PgBouncer delante), el primer cuello de botella real de escalabilidad será agotar conexiones de Postgres, no la base en sí.

  **✅ Resuelto (2026-08-09, punto 16).** Ver recomendación 2 más abajo.
- **Discrepancia entre documentación de infraestructura y configuración real actual.** `docs/apidian-architecture.md:2727-2742` describe un plan de despliegue en **Railway** ("Backups: Railway Postgres incluye snapshots automáticos. Suficiente para la fase inicial.") — pero `erp/.env.example` ya apunta a **Neon** como Postgres de producción y menciona SMTP en **servidor propio con systemd**, un modelo de infraestructura distinto (self-hosted, no Railway). No quedó claro cuál es el estado real vigente; si el plan de Railway quedó obsoleto, la afirmación de "backups automáticos suficientes" también quedó obsoleta y no hay nada que la reemplace (ver más abajo).
- **Sin límite/paginación forzada visible a nivel de pool que prevenga que un tenant grande degrade a los demás** — no se evaluó a fondo (fuera de alcance de una revisión de paso), pero al ser un pool único compartido por todos los tenants sin `SET LOCAL statement_timeout` ni límites de recursos por rol/tenant, una consulta pesada de una empresa (ej. reportes contables grandes) puede consumir conexiones que afectan a las demás.

## ❌ Lo que falta por completo

- **Sin Dockerfile, sin docker-compose, sin manifiestos de Kubernetes, sin `.github/workflows`.** Confirmado de nuevo con búsqueda directa en todo el repo (`find . -iname "Dockerfile*" -o -iname "docker-compose*" -o -path "*/.github/workflows/*"`): cero resultados. Tampoco hay `.gitlab-ci.yml`, `Jenkinsfile`, ni ningún otro sistema de CI/CD.

  **✅ Resuelto parcialmente (2026-08-09) — CI mínimo, no despliegue.** Nuevo `.github/workflows/ci.yml`: job `backend` (Postgres de servicio, `go vet`/`go build`/`go build -tags=integration` en `erp` y `cofacture`, levanta el server real contra el Postgres del job para aplicar las migraciones de los 14 módulos, corre `go test ./... -tags=integration` y `govulncheck` en ambos módulos Go) y job `frontend` (`npm run lint`, `npm run build`, `npm audit --audit-level=high` no bloqueante — ver punto 20 pendiente). Sigue sin haber Dockerfile/docker-compose/manifiestos — este punto solo cubre integración continua (validar cada push), no empaquetado ni despliegue continuo, que siguen pendientes (ver punto 18 del plan de acción).
- **Sin ningún script de deploy en el repo** (`*.sh`, `*.ps1` fuera de `docs/reference`): no hay `deploy.sh`, no hay unit file de systemd versionado (`*.service`), no hay ningún artefacto que documente cómo se construye/levanta el binario en el servidor real más allá de comentarios sueltos en `.env.example`. El despliegue actual, si existe, vive fuera del repositorio (en la memoria de quien lo hizo) y no es reproducible por otra persona.
- **Sin estrategia de backup ni recuperación ante desastres implementada ni documentada de forma operativa.** La única mención es la línea de `docs/apidian-architecture.md:2742` sobre snapshots automáticos de Railway — que, como se señaló arriba, contradice la configuración actual con Neon/servidor propio. No hay ningún script de `pg_dump`, cron job, ni documento de runbook para restaurar la base ante un fallo. Si hoy la producción corre sobre Neon, Neon sí ofrece point-in-time recovery en sus planes pagos, pero **no hay evidencia en el repo de que esté configurado, verificado o documentado** — es una suposición, no un hecho confirmado.
- **Sin monitoreo ni alertas centralizadas.** No hay Sentry, Datadog, Prometheus, ni ninguna integración de este tipo en `erp/go.mod` (dependencias directas: solo `golang-migrate`, `google/uuid`, `jackc/pgx/v5`). Hay trazas de OpenTelemetry en `erp/go.sum` (`go.opentelemetry.io/otel`, `otelhttp`) pero son **dependencias indirectas/transitivas** (arrastradas por otra librería, probablemente `chromedp`), no una instrumentación real: no se encontró ningún `otel.Tracer`, `otel.Meter` ni `otelhttp.NewHandler` usado en el código de `erp`. El único logging es `erp/internal/shared/logger` (probablemente `slog` a stdout), sin agregación ni alertas.
- **Sin health check de dependencias** (ver arriba): no hay verificación de conectividad a Postgres, SMTP, ni al servicio TRM (`TRM_API_URL`) expuesta en ningún endpoint.

## 🔧 Recomendaciones concretas y accionables

1. Convertir `/health` en un healthcheck real: agregar `pool.Ping(ctx)` con timeout corto y devolver `503` si falla, antes de depender de este endpoint para cualquier automatización de reinicio o balanceo.
2. **✅ Implementado (2026-08-09, punto 16 del plan de acción).** Fijar explícitamente `cfg.MaxConns`/`cfg.MinConns` en `mustOpenDB` (`erp/cmd/server/main.go`) — ahora `MaxConns=20`, `MinConns=2`, `MaxConnIdleTime=5m`. Valores de partida razonables para el volumen actual (pre-producción); revisar contra los límites reales de Neon cuando haya tráfico de clientes.
3. Resolver la discrepancia Railway vs. Neon/systemd en la documentación: actualizar o eliminar la sección de `docs/apidian-architecture.md:2727-2742` para que refleje la infraestructura real vigente, y documentar explícitamente la estrategia de backup real (¿point-in-time recovery de Neon activado? ¿con qué retención?) en vez de heredar una afirmación sobre una plataforma que ya no se usa.
4. Versionar en el repo (aunque sea en `docs/deploy/` o similar) el unit file de systemd real usado en producción y un script mínimo de deploy (pull + build + restart), para que el despliegue no dependa exclusivamente del conocimiento de una persona.
5. Si se anticipa crecimiento de tenants, evaluar PgBouncer delante de Postgres (más relevante aún si el proveedor es Neon, que ya ofrece pooling gestionado vía su propio "pooler" — el propio `.env.example` menciona `host-pooler.neon.tech`, lo cual sugiere que esto ya se consideró parcialmente pero conviene confirmarlo explícitamente).
6. Agregar como mínimo logging estructurado con un nivel de alerta accionable (ej. Sentry para errores no controlados) antes de tener el primer cliente real de pago — hoy un fallo en producción solo se detecta si alguien está mirando los logs del proceso en el momento en que ocurre.
