# Agente de Base de Datos (PostgreSQL con esquemas)

Auditoría basada en la lectura de migraciones reales de `accounting`, `electronic`, `purchase`, `sales`, `inventory`, `catalog`, `security`, `company`, `audit`, `stats`, más el código de `erp/internal/shared/tenant` y varios repositorios de infraestructura.

### ✅ Lo que está bien implementado

- **Modelo real: un schema Postgres por módulo + multi-tenant por columna `company_id` dentro de cada schema.** No es "schema por tenant". Cada módulo ejecuta `CREATE SCHEMA IF NOT EXISTS <modulo>` en su propia migración (confirmado en `accounting/.../000001_accounting.up.sql:7`, `sales/.../000001_sales.up.sql:6`, `electronic/.../000001_electronic.up.sql:1`, y así en los 14 módulos con persistencia). Dentro de cada schema, las tablas de negocio tienen columna `company_id UUID NOT NULL` (todas las tablas revisadas de `sales`, `purchase`, `electronic`, `accounting`, `inventory`) y las queries de los repositorios siempre filtran por ella — verificado con grep en `sales/infrastructure/persistence/postgres/{repository,payment_repository,quote_repository}.go`: todo `SELECT`/`UPDATE`/`DELETE` lleva `WHERE ... AND company_id=$N` o `WHERE company_id=$1`. El aislamiento de tenant no depende solo de que el caso de uso reciba el `companyID` correcto desde el JWT (`shared/tenant/context.go`); está reforzado a nivel de SQL en el propio repositorio.

- **Herramienta de migraciones real y versionada: `golang-migrate/migrate/v4`, no un runner casero.** Confirmado en `erp/go.mod:6` (`github.com/golang-migrate/migrate/v4 v4.19.1`) y en el patrón repetido `erp/internal/*/infrastructure/persistence/postgres/migrate.go`: usa `iofs` sobre `//go:embed migrations/*.sql`, driver `pgx/v5`, y — detalle importante — cada módulo usa su **propia tabla de control de versión** (`x-migrations-table=sales_schema_migrations`, `accounting_schema_migrations`, etc., una por módulo), lo que permite versionar cada módulo de forma independiente sin que se pisen entre sí. `erp/cmd/server/main.go:113-126` las corre todas al arrancar el servidor, en orden de dependencia lógica (catalog → security → company → saas → thirdparty → product → inventory → purchase → sales → accounting → electronic → payroll → hr → audit).

- **Buena normalización y uso de constraints en los módulos transaccionales núcleo.** `accounting/.../000001_accounting.up.sql` (461 líneas) tiene: `CHECK (level BETWEEN 1 AND 6)` en cuentas, `CHECK (status IN (...))` en períodos/asientos, `CHECK (debit >= 0)`/`CHECK (credit >= 0)` + `CONSTRAINT chk_line_amounts` que impide una línea contable con débito y crédito simultáneos (líneas 85-95), `UNIQUE (company_id, year, month)` en períodos, FK internas correctas (`journal_lines.account_id → accounting.accounts.id`, `journal_lines.journal_id → accounting.journal_entries.id`). `inventory/.../000001_inventory.up.sql` tiene `UNIQUE (company_id, product_id, warehouse_id)` en `inventory.stock`, correcto para impedir filas de stock duplicadas.

- **Índices presentes en las columnas de filtro obvias de los módulos de mayor volumen.** `electronic.documents` tiene `idx_documents_company`, `idx_documents_status (company_id, status)`, `idx_documents_issue_date (company_id, issue_date DESC)` y un índice único parcial `idx_documents_document_key (company_id, document_key) WHERE document_key IS NOT NULL` (evita CUFE/CUDE duplicado por empresa). `accounting.journal_entries` tiene 5 índices distintos incluyendo parciales (`WHERE voucher_number IS NOT NULL`, `WHERE book != 'BOTH'`), que son un buen patrón para evitar inflar el índice con el caso por defecto.

- **Contadores de numeración con upsert atómico (`INSERT ... ON CONFLICT ... RETURNING`), no lectura-luego-escritura.** `erp/internal/purchase/infrastructure/persistence/postgres/repository.go:207-211` genera el siguiente consecutivo con `INSERT INTO purchase.number_counters (...) ON CONFLICT (...) DO UPDATE SET last_seq = last_seq + 1 RETURNING last_seq`, que es seguro bajo concurrencia gracias al lock de fila implícito del `ON CONFLICT`, sin necesitar `SELECT ... FOR UPDATE` explícito ni una transacción manual en el caso de uso.

- **`erp` y `cofacture` NO comparten base de datos porque `cofacture` no tiene base de datos.** Se verificó que no existe ni una sola referencia a `database/sql`, `pgxpool` o `sql.DB` en todo el árbol `cofacture/` (`grep -rl` vacío) ni carpetas de migraciones. `cofacture` es una librería pura (builder/firma/envío SOAP/QR/zip) sin estado persistente; toda la persistencia del documento electrónico (borrador, XML firmado, estado DIAN) la hace `erp/internal/electronic` después de invocar las funciones puras del adaptador (`erp/internal/electronic/infrastructure/cofacture/adapter.go`). Consecuencia práctica: **no existe ningún riesgo de consistencia transaccional entre dos bases de datos**, porque solo hay una (la de `erp`). El único punto de atomicidad real a vigilar es interno a `erp`: la secuencia "firmar (cofacture, en memoria) → enviar a DIAN (SOAP, red) → persistir resultado (Postgres)" en `electronic/application/confirm.go`, donde un fallo entre el envío SOAP y el `UPDATE` del documento sí podría dejar un documento aceptado por la DIAN pero no reflejado como tal en la BD — pero eso es un problema de fiabilidad de un solo flujo, no de dos bases de datos descoordinadas.

### ⚠️ Lo que existe pero tiene problemas / riesgos

- **Violación de encapsulamiento de schema vía JOIN/subquery SQL directo entre módulos — severidad media-alta (mismo hallazgo que en el informe de arquitectura, aquí con foco en el impacto de BD).** Tres repositorios hacen SQL contra un schema que no es el suyo:
  - `company/infrastructure/persistence/postgres/repository.go:111`: `SELECT company_id FROM security.user_companies WHERE user_id = $1` dentro de una subquery de `ListByUserID`.
  - `audit/infrastructure/persistence/postgres/repository.go:56` y `:67`: `LEFT JOIN security.users u ON u.id = ae.user_id`.
  - `stats/infrastructure/persistence/postgres/repository.go:71,98,142`: `FROM electronic.documents` en tres queries de `GetBillingStats`.
  
  Esto es inconsistente con el propio principio de diseño que el equipo documentó en los comentarios de migración de `sales` y `purchase` ("cada módulo es dueño de su schema... sin FK a propósito"): a nivel de integridad referencial (FK) se respeta la frontera, pero a nivel de lectura (JOIN) no. Además, técnicamente, en Postgres esto solo funciona porque las migraciones dejan todo en la misma base de datos física con `search_path=public` y los schemas son simplemente namespaces visibles entre sí — si en el futuro se decidiera separar módulos en bases de datos físicas distintas (para escalar independientemente), estas 3 queries romperían inmediatamente y de forma no evidente en el código Go (el error aparecería en runtime como "schema security does not exist").

- **Faltan migraciones `.down.sql` en 4 de 14 módulos — severidad baja-media.** Verificado exhaustivamente: `accounting`, `audit`, `catalog`, `company`, `inventory`, `product`, `purchase`, `sales`, `security`, `thirdparty` tienen su `.down.sql`; **`electronic`, `hr`, `payroll` y `saas` no tienen ningún `.down.sql`**. Como cada `.down.sql` existente es simplemente `DROP SCHEMA IF EXISTS <modulo> CASCADE` (verificado en `accounting/.../000001_accounting.down.sql`), la ausencia no es grave para revertir en desarrollo (se puede volar el schema a mano), pero si alguna vez se invoca `migrate down` mediante la librería (o una herramienta que dependa de que todo `.up` tenga su `.down`), fallará para esos 4 módulos.

- **Ausencia de `UNIQUE (company_id, number)` en documentos con numeración de negocio — severidad media.** `sales.sales.number` (`sales/.../000001_sales.up.sql:12`) y `purchase.orders.number` (`purchase/.../000001_purchase.up.sql:12`) son `TEXT NOT NULL DEFAULT ''` sin ninguna restricción de unicidad, pese a que se generan desde una tabla de contador dedicada (`sales.number_counters` / `purchase.number_counters`). El contador en sí es atómico (ver hallazgo positivo arriba), pero no hay red de seguridad a nivel de BD: si un bug futuro en el caso de uso reintenta una inserción sin pedir número nuevo, o si alguien inserta manualmente un registro con un número repetido, Postgres no lo va a impedir. Es defensa en profundidad ausente, no una vulnerabilidad activa hoy.

- **JSONB usado como almacenamiento primario para datos que se consultan también en agregados — riesgo bajo, a vigilar.** `electronic.documents` (`electronic/.../000001_electronic.up.sql:37-60`) guarda `customer`, `lines`, `payment_means`, `billing_reference`, `discrepancy_response`, `supplier`, `withholding_taxes` como columnas `JSONB`, en vez de tablas normalizadas (`document_lines`, etc.). Es una decisión defendible (el XML DIAN firmado es inmutable una vez emitido, y desnormalizar evita joins para reconstruir el documento legal tal cual se envió), pero implica que `stats/infrastructure/persistence/postgres/repository.go` no puede filtrar/agrupar por líneas o impuestos individuales sin parsear JSON en SQL; hoy sus 3 queries solo usan columnas escalares (`totals_payable_cents`, `status`, `issue_date`), así que el diseño actual no sufre por esto, pero limita reportes futuros más finos (p. ej. "ventas por producto" tendría que ir a `sales.sale_lines`, no a `electronic.documents`).

### ❌ Lo que falta por completo

- **No se encontró ningún índice sobre las columnas FK que no son la clave de filtrado principal**, por ejemplo `electronic.documents.numbering_range_id`, `electronic.documents.customer_id`, `electronic.documents.supplier_id` (todas sin índice propio, solo cubiertas indirectamente por el índice de `company_id`). Con el volumen bajo actual no es un problema, pero si `numbering_range_id` se usa para joins frecuentes (p. ej. reportes de consumo de resolución DIAN), faltará index.
- **No hay pool de conexiones ni configuración de límites explícita más allá del default de `pgxpool`** — `mustOpenDB` en `erp/cmd/server/main.go:489-512` no fija `MaxConns`/`MinConns`/`MaxConnIdleTime` en el `cfg`; queda en los defaults de la librería. No es incorrecto, pero para un ERP multi-tenant con 15+ módulos migrando y sembrando datos al arranque sobre el mismo pool, vale la pena revisar si el default es suficiente bajo carga real.
- **No hay ningún mecanismo de row-level security (RLS) de Postgres como segunda capa de aislamiento de tenant.** Todo el aislamiento multi-tenant depende de que cada repositorio recuerde poner `WHERE company_id = $N` — se verificó que hoy lo hacen de forma consistente, pero no hay ninguna política `CREATE POLICY` en las migraciones que actúe como red de seguridad si un desarrollador futuro olvida el filtro en una query nueva.

### 🔧 Recomendaciones concretas y accionables

1. Aplicar la misma recomendación del informe de arquitectura: reemplazar los 3 JOIN/subquery cross-schema (`company`→`security.user_companies`, `audit`→`security.users`, `stats`→`electronic.documents`) por llamadas a puertos Go del módulo dueño, para que el acoplamiento quede explícito en el código Go y no escondido en SQL.
2. Añadir `000001_electronic.down.sql`, `000001_hr.down.sql`, `000001_payroll.down.sql`, `000001_saas.down.sql` con el mismo patrón `DROP SCHEMA IF EXISTS <modulo> CASCADE;` que ya usan los otros 10 módulos, por consistencia y para que `migrate down` no falle si alguna vez se usa.
3. Agregar `ALTER TABLE sales.sales ADD CONSTRAINT uq_sales_number UNIQUE (company_id, number) WHERE number != ''` (e idéntico para `purchase.orders`) — constraint condicional para no romper los borradores que hoy usan `number=''` por defecto.
4. Añadir índices sobre `electronic.documents.numbering_range_id`, `customer_id`, `supplier_id` si los reportes de rangos DIAN (`erp/internal/electronic/application/get_dian_ranges.go`) empiezan a filtrar/agrupar por esas columnas — no urgente con el volumen actual, pero barato de añadir ahora en la misma migración consolidada.
5. Fijar explícitamente `MaxConns` en `pgxpool.Config` en `mustOpenDB` (`erp/cmd/server/main.go:489`), calculado en función del número de módulos que abren queries concurrentes al arrancar (migraciones + seeds se ejecutan secuencialmente hoy, pero en producción con tráfico real el pool compartido por 15 módulos merece un límite explícito y monitoreado, no el default implícito de la librería).
6. Evaluar RLS de Postgres (`CREATE POLICY ... USING (company_id = current_setting('app.company_id')::uuid)`) como defensa en profundidad para el multi-tenant por columna, dado que hoy el único guardián es la disciplina del desarrollador en cada repositorio.
