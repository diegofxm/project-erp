# Agente Frontend

Alcance revisado: `frontend/package.json`, `frontend/src/App.tsx`, `frontend/src/lib/apiClient.ts`, `frontend/src/context/AuthContext.tsx`, `frontend/src/components/ProtectedRoute.tsx`, `frontend/src/components/ConnectionBanner.tsx`, `frontend/src/components/DashboardLayout.tsx`, `frontend/src/components/Sidebar.tsx`, `frontend/src/components/ui/*`, y muestreo de páginas reales (`CustomersPage.tsx`, `DashboardPage.tsx`, `LoginPage.tsx`, `SettingsActivityPage.tsx`), comparado contra las rutas HTTP reales de `erp/internal/{security,catalog,thirdparty}/interfaces/http/routes.go`.

### ✅ Lo que está bien implementado

- **Stack real**: React 19.2 + react-router 7 (`BrowserRouter`/`Routes`) + Tailwind 4, sin librería de estado global — todo el estado de servidor se maneja con `useState`/`useEffect` por página y contextos de React puros (`AuthContext.tsx`, `ThemeContext.tsx`, `ToastContext.tsx`, `ConfirmContext.tsx`, `NotificationContext.tsx`). No hay Redux/Zustand/React Query/SWR — confirmado en `frontend/package.json` (deps: `react`, `react-dom`, `react-router`, `recharts`, `react-grid-layout`, `tailwindcss`, `lucide-react`, `qrcode`; sin nada de fetching/caching).
- **Sistema de componentes base real y usado**: `frontend/src/components/ui/` (Button, Input, Select, Combobox, Card, Banner, Spinner, Pagination, Breadcrumbs, ConfirmDialog, Toast, StatusPill, Tabs, TagInput, etc.). `Button.tsx` y `Input.tsx` están efectivamente adoptados — `LoginPage.tsx:45-62` los usa correctamente con `label`, `autoComplete`, `required`. Grep de `aria-label`/`<label`/clases responsive muestra adopción amplia (189 usos de `sm:`/`md:`/`lg:` en 54 archivos), no solo en 2-3 páginas de ejemplo.
- **Sesión persistida correctamente re-verificada al cargar**: `AuthContext.tsx:127-153` (`verifySession`) no solo restaura el token de `localStorage`, sino que llama `/auth/me` para refrescar campos que cambian fuera de un login normal (ej. `is_superadmin`), y hace `logout()` automático si la API responde 401/404 (`AuthContext.tsx:147`).
- **Distinción real entre "sin red" y "sesión inválida"**: `ConnectionBanner.tsx` se muestra solo cuando falla la conexión (no HTTP 401), evitando cerrar sesión falsamente por caída de red — comentario explícito en `ConnectionBanner.tsx:5-8`.
- **Responsividad del layout principal**: `DashboardLayout.tsx` implementa un sidebar de escritorio (`hidden md:flex`) y un drawer móvil con backdrop y animación (`DashboardLayout.tsx:44-63`), con lógica de breakpoint real (`< 768` = drawer, `< 1024` = colapsado por defecto, `DashboardLayout.tsx:17,27`). No es un layout fijo de escritorio.
- **Módulos backend con cobertura frontend confirmada**: accounting, catalog (consumido como datos de referencia vía `lib/useCatalog.ts`, `lib/ciiu.ts`), company, electronic (facturación electrónica: invoices/credit-notes/debit-notes/support-documents/adjustment-notes), inventory, product, purchase, saas (`AdminPage.tsx` — billing/plans/renewals), sales, thirdparty (customers/suppliers), audit (`SettingsActivityPage.tsx`), security (login/registro/invitación/roles owner-admin-member vía `useCanManage.ts`).

### ⚠️ Lo que existe pero tiene problemas / riesgos

- **Token JWT en `localStorage` en texto plano, sin partición de riesgo XSS — severidad alta.** `AuthContext.tsx:14,49,64` (`STORAGE_KEY = "apidian.session"`, `readStoredSession`/`writeStoredSession` usan `localStorage.getItem/setItem` directo) guardan `{ token, user, company }` completo. Cualquier XSS (ej. una librería de terceros comprometida, o un `dangerouslySetInnerHTML` futuro — hoy no encontré ninguno) podría leer `localStorage` y robar el token sin necesidad de interceptar tráfico. No usa `httpOnly` cookie ni almacenamiento en memoria con refresh silencioso.
- **No hay refresh token — sesión expira y ya, sin aviso proactivo — severidad media.** No se encontró ningún mecanismo de refresh en `AuthContext.tsx` ni en `apiClient.ts` (busqué "refresh" y no hay resultados relevantes de renovación de token). `verifySession()` solo corre una vez al montar la app (`AuthContext.tsx:155-165`) y en `retryConnection()` manual desde el banner. Si el JWT expira mientras el usuario navega, cualquier llamada a la API en una página normal (ej. `CustomersPage.tsx:30-33`) recibe 401, pero **no hay interceptor global de 401** en `apiClient.ts` — el único sitio donde un 401 fuerza `logout()` es dentro de `verifySession()` (`AuthContext.tsx:147`). En el resto de páginas, un 401 solo cae en el `catch` local y se muestra como "No se pudieron cargar los clientes" (mensaje genérico de error de datos), dejando al usuario confundido en vez de redirigirlo a `/login`.
- **Sin timeout de red en `apiClient.ts` — severidad media.** `request()` (`apiClient.ts:18-34`) y `getBlob()` (`apiClient.ts:39-51`) llaman `fetch()` sin `AbortController` ni `signal` con límite de tiempo (confirmé con grep de `AbortController|timeout|signal` en todo `src/`: cero resultados). Si el backend Go se cuelga, el `fetch` nunca resuelve y el `loading`/`Spinner` de la página queda girando indefinidamente sin mensaje de error.
- **Patrón de loading/error no está centralizado — cada página lo reimplementa a mano — severidad baja/media.** No existe ningún hook compartido tipo `useApiFetch`/`useAsync` (grep sin resultados). Comparando `DashboardPage.tsx:177-187` (usa flag `cancelled` para evitar `setState` tras desmontar, y hace `return` temprano en loading/error reemplazando toda la página) contra `CustomersPage.tsx:29-35` (`refresh()` sin cancelación, y el spinner de carga se muestra inline dentro del layout, no reemplaza la página) — dos convenciones distintas para el mismo problema. Riesgo de warnings de React por `setState` en componente desmontado en páginas que no usan el patrón `cancelled`.
- **Accesibilidad de controles icon-only inconsistente — severidad baja/media.** Los botones de acción de tabla (editar/eliminar) usan `title="Editar"` / `title="Eliminar"` (`CustomersPage.tsx:156,160`) en vez de `aria-label` — `title` no es anunciado de forma consistente por lectores de pantalla ni por navegación táctil. El input de búsqueda de `CustomersPage.tsx:105-111` es un `<input>` crudo con solo `placeholder`, sin `<label>` ni `aria-label` asociado (el placeholder desaparece al escribir y no sustituye a un label real). `aria-label` en general solo aparece en 24 ocurrencias repartidas en 9 archivos de todo `src/` — la mayoría en páginas de documentos, no es un patrón aplicado de forma pareja.
- **`Combobox.tsx` no expone semántica ARIA de combobox.** Tiene buen soporte de teclado (flechas, Enter, Escape — `Combobox.tsx:50-69`), pero le faltan `role="combobox"`, `aria-expanded`, `aria-controls`, `aria-activedescendant` — un lector de pantalla no lo anuncia como combobox, solo como texto libre.
- **Duplicación conceptual Customer/Supplier en frontend pese a unificación en backend.** El backend unifica cliente+proveedor en `thirdparty` (según arquitectura documentada), pero el frontend mantiene `CustomerForm.tsx`, `SupplierForm.tsx`, `CustomersPage.tsx`, `SuppliersPage.tsx` como código separado y no un componente parametrizado único — no es un bug, pero es duplicación de UI que diverge del modelo de dominio unificado y multiplica el mantenimiento a futuro.

### ❌ Lo que falta por completo

- **Nómina y RRHH (`payroll`, `hr`) sin ninguna vista frontend — confirmado explícitamente en el código.** `Sidebar.tsx:53-59` define el grupo "Nómina y RRHH" con los tres ítems (`/payroll`, `/hr`, `/employees`) marcados `disabled: true`, y el comentario en `Sidebar.tsx:17-18` lo documenta sin ambigüedad: *"Sin página propia todavía (ej. Nómina/RRHH/Empleados — módulo backend existe, sin frontend)"*. No existen `PayrollPage`, `HrPage` ni `EmployeesPage` en `frontend/src/pages/`, ni rutas correspondientes en `App.tsx`.
- **Sin gestión granular de roles/permisos (RBAC) en el frontend.** El backend de `security` (`erp/internal/security/interfaces/http/routes.go`) solo expone auth básico (login/registro/perfil/invitación/selección de empresa) — no hay endpoints de roles/permisos más allá de owner/admin/member, y el frontend refleja exactamente ese límite (`useCanManage.ts` solo diferencia owner/admin de member, sin pantalla de administración de roles). Esto es consistente con el estado documentado del backend (RBAC pendiente), no es una carencia exclusiva del frontend, pero se confirma que tampoco hay ninguna vista adelantada para ello.
- **Sin interceptor HTTP global (401 / reintentos / timeout) en `apiClient.ts`.** Confirmado arriba como riesgo, pero listado también aquí como ausencia total: no hay wrapper de reintento, no hay cola de refresco de token, no hay bloqueo de solicitudes concurrentes tras un 401.
- **Sin tests de frontend.** No se encontró ningún archivo `*.test.tsx`/`*.spec.tsx` ni configuración de test runner (no hay `vitest`/`jest` en `package.json`, y `npm run lint` solo corre `oxlint`). Esto es coherente con lo ya registrado como pendiente para el proyecto (tests unitarios frontend), pero se confirma explícitamente aquí.

### 🔧 Recomendaciones concretas y accionables

1. Añadir un interceptor centralizado en `apiClient.ts`: si cualquier respuesta es 401, llamar automáticamente `setAuthToken(null)` + emitir un evento (o exponer un callback registrado desde `AuthContext.tsx`) que dispare `logout()` y redirija a `/login`, en vez de dejar que cada página muestre un mensaje de error genérico.
2. Agregar timeout a `fetch()` en `request()` y `getBlob()` (`apiClient.ts:18,39`) usando `AbortController` con, por ejemplo, 15-20s, y mapear el abort a un `ApiError` con mensaje "Tiempo de espera agotado" para que el spinner nunca quede infinito.
3. Evaluar mover el JWT fuera de `localStorage` — al menos separarlo de los datos de usuario/empresa (que sí pueden ir en `localStorage`), y mantener el token en memoria + cookie `httpOnly`/`SameSite=Strict` si el backend puede emitirla, para reducir superficie de robo por XSS.
4. Extraer un hook compartido (`useApiResource` o similar) que encapsule el patrón `loading/error/cancelled` visto repetido con variaciones en `CustomersPage.tsx` y `DashboardPage.tsx`, para que todas las páginas nuevas (incluyendo las de nómina/RRHH cuando se construyan) partan de un único patrón.
5. Reemplazar `title="Editar"/"Eliminar"` por `aria-label` en botones icon-only de todas las páginas de listado (patrón visto en `CustomersPage.tsx:156,160` se repite en `SuppliersPage.tsx`, `ProductsPage.tsx`, etc. — no se auditó archivo por archivo pero es el mismo componente de tabla replicado); añadir `aria-label` o `<label className="sr-only">` a los inputs de búsqueda crudos.
6. Cuando se implemente el frontend de nómina/RRHH, seguir el mismo layout de `Sidebar.tsx` (ya tiene el grupo reservado) y usar el sistema `components/ui/` existente en vez de crear controles nuevos, dado que la adopción actual del kit ya es alta y consistente donde se usa.
